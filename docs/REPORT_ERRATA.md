# Report errata

`TrialGuard_Project_Report.pdf` was written for the hackathon submission and is left unchanged. This file lists statements in it that do not match the code in this repository. Page numbers refer to the 5-page PDF. The README (see [RAG status](../README.md#rag-status) and [Known limitations](../README.md#known-limitations)) describes the current state of the code.

| # | Report says | Where | What the repo shows |
|:--|:---|:---|:---|
| 1 | The orchestrator fetches the protocol "through a RAG MCP Server backed by a Chroma vector store"; agents fetch protocol data through the "RAG MCP Server". | p1 abstract; p2 architecture and tech-stack list | There is no RAG MCP server. `packages/mcp-rag` contains only a `pyproject.toml`. Retrieval code lives in `services/rag_service` and is called in-process from `apps/orchestrator/nodes/rag_node.py`. |
| 2 | The Protocol Compliance agent "queries the RAG MCP server to retrieve verbatim clauses from the trial protocol using explicit trial-id metadata filtering". | p2, section 6.2 | In the deployed gateway path the Compliance agent receives a small set of fixed clauses written in `_simulated_rag_output` (`apps/gateway/routers/orchestrator.py`); nothing is retrieved. The trial-id metadata filter exists in `Retriever.retrieve_trial` (`services/rag_service/src/rag/retriever.py`), which the gateway does not call. |
| 3 | The agent provides "exact page-level citations for every detected deviation". | p2, section 6.2 | No page information is stored. Indexed chunk metadata is `trial_id`, `section` and `source` only (`services/rag_service/src/rag/vector_store.py`). |
| 4 | "The pipeline works end to end and is built to run on real protocol documents and real patient records without any changes." | p1 abstract (also echoed under Table 3, p4) | Not demonstrated. The live path never reads protocol documents, and the retrieval corpus is 4 trials / 40 eligibility chunks. The raw ClinicalTrials.gov and FDA label inputs that the ingestion scripts expect are not in the repo. No test or evaluation runs the pipeline on real protocols or real patient records. |
| 5 | Table 1 gives TrialGuard figures such as a protocol deviation catch rate "Targeted >=95%", review latency "3-8 seconds" and ">80% workload reduction", next to baseline figures for other methods. | p3, Table 1 | These are design targets. No benchmark script, test or result file in the repo measures any of them, and the baseline columns carry no citation. The README already says this under Limitations & Future Work. |
| 6 | Table 3 lists "RAG (Chroma, Trial-ID-keyed)" as Implemented as part of the end-to-end pipeline. | p4, Table 3 | The retrieval code exists and has been built, but it is not part of the running app. The README's Implementation Status lists it under "Built but not used by the running app". |

If you only read one line: the report's RAG MCP server and retrieval-backed Compliance agent describe the intended design. The running demo uses fixed protocol clauses.
